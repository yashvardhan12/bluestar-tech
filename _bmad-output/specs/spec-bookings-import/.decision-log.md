# Decision log — SPEC-bookings-import

## 2026-08-29 · create

Distilled from a working session that had already settled every design decision
against the live database (project `pmuppvvhcafrgfysubtc`) and the real sample
file. No elicitation: input was rich, so extraction was direct.

**Pass 1 — Coherence.** Eight capabilities, each with `intent` and `success`;
every success criterion is decidable against the sample file or the live schema.
Constraints all bend a decision — each rules out a specific implementation that
would otherwise be the obvious choice (`Trip ID` grouping, `Total amount` as
`base_rate`, writing `status`, matching customers on name). Seven non-goals,
each traceable to a verified absence in the file or an explicit user decision.
Success signal is a demonstrable sequence, not a metric. Three open questions
survive; all are judgement calls no amount of analysis resolves.

**Pass 2 — Preservation.** Load-bearing content routed as: the 59-column
mapping to `field-mapping.md`; the duty-type key, naming convention and
derivable rate card to `duty-type-matrix.md`; the 14 guards to `safeguards.md`;
regression numbers to `sample-baseline.md`. `project-context.md` is adopted, not
duplicated. Nothing load-bearing was dropped.

Wrapper-only content dropped: conversational framing, the sequence in which
findings were discovered, and two superseded positions — an earlier plan to land
predated duties as `Completed`, and an earlier plan to referee dates against the
`Month` column. Both were tested and withdrawn; the withdrawal of the `Month`
check is recorded in `safeguards.md` because it would otherwise be re-proposed.

**Verdict.** Complete and consistent. The spec describes no code that exists
beyond `src/lib/importDutyTimes.ts` and migrations 031/032; the importer itself
is unbuilt.

## 2026-08-29 · update — open questions resolved

All three open questions answered by the user; the section is now empty.

**`Superium Deluxe`.** Not a fold. It is reported as an unresolved car type like
any other missing reference, and the operator either corrects the sheet or adds
the vehicle group. This removes a judgement call rather than making one, and it
is consistent with the standing rule that the import never invents reference
data. Recorded in `duty-type-matrix.md`; the baseline stays at 21 missing duty
types rather than 19.

**Duty-less bookings.** The cause is the ordinary interrupted run, not an exotic
failure: one import is roughly 700 sequential round trips with no client-side
transaction, so a dropped connection leaves exactly one in-flight booking with
its row written and no duties. Skipping on `booking_ref` alone strands it
permanently. Settled as a one-line condition — the skip test is "booking exists
**and** has duties" — which downgrades this from an architecture decision and
removes the RPC from scope. Constraint rewritten; `safeguards.md` item 12
rewritten.

**Ambiguous duty windows.** No resolution flow. They are listed last, in their
own closing section, and left to the operator. Added as a non-goal so a
downstream skill does not build a picker for two rows.

**Verdict.** Kernel unchanged in shape: 8 capabilities, 13 constraints, 8
non-goals, no open questions. Two capability success criteria tightened (CAP-4
names the unresolved-car-type case, CAP-6 names the duty-less repair) rather
than added, so IDs are untouched. The preflight mock was updated to match.

## 2026-08-29 · update — money leaves scope

The import writes no money. Amounts are derived by the system when a duty, or
all duties in a booking, complete; the client's settled figures are read past,
not stored.

CAP-8 (reconciliation) removed — 7 capabilities remain, IDs 1–7 unchanged. The
`base_rate` constraint now states that no money is written. `Total amount`,
`Revenue amount`, `Toll Tax` and `Parking Charge` move fully into the no-home
bucket. The per-trip multiplication trap is kept as a footnote in
`field-mapping.md` rather than deleted, because it only stops being a trap while
the column stays unimported. Safeguards lost the reconciliation step and the
`round2()` rule; gained "write no money". The money section of
`sample-baseline.md` is gone, as is the money panel in the preflight mock.

The rate-card derivation in `duty-type-matrix.md` **stays**, with its purpose
made explicit: those rates seed `duty_types`, not imported duties. The
derivation feeding the card is what the completion-time calculation reads from.

**Dependency now on the critical path.** That completion-time calculation does
not exist yet. `duties.base_rate` is operator-entered in the booking drawer
today, and `buildClosePayload` writes `closed_at`, `end_odo`, `status`,
`closed_by_profile` and `corrected_at` — no amount. Per project-context rule 7,
`invoice.ts` sums `duties.base_rate` alone and the `duty_types` rate card is
dead at invoice time. Until that derivation is built, imported duties carry a
null `base_rate` and invoice as zero.

**Verdict.** Kernel consistent: 7 capabilities, 12 constraints, 9 non-goals, no
open questions. Scope is narrower and the spec is simpler for it.

## 2026-08-29 · update — vehicles out, closing stays manual

Two related decisions, both the user's.

**Vehicles are not imported.** The export's `Daily Journey Vehicle Number` holds
placeholders, and allotment is an operator action on the created duties. Column
L moves to the no-home bucket (19 mapped, 15 no-home). This reverses a position
argued earlier in the session for a reason that no longer applies: the argument
was that a matched vehicle lets `duties_status` derive Completed for free. With
placeholders that derivation would be built on fiction.

**Duties are not closed by the import.** Operators close them in the system by
hand, with whatever evidence they actually have.

**Consequence, recorded as an assumption.** With no vehicle, `duties_status`
falls to `else d.status` and every imported duty reads `Booked`. All 1,073 enter
the allotment queue in one action. That is the intent — allotment is the next
operator step — but it is a large queue arriving at once.

The sequence is coherent: import lands `Booked` and unallotted → operator allots
→ the duty is predated, so `duties_status` derives `Completed` immediately →
`isCloseable` gates on `closed_at`, not status, so the Close action stays
available and the operator closes with real evidence. `dutyClose.ts` already
documents this exact case ("a back-dated allotment reads Completed through
duties_status while carrying an empty slip"), so the codebase anticipated it.

The preflight mock needed no change — it never resolved vehicles.

**Verdict.** 7 capabilities, 13 constraints, 9 non-goals, no open questions.

## 2026-08-29 · update — built, and two duplicate guards added

Implemented: `dutyWindows.ts`, `createBooking.ts`, `importBookings.ts`,
`ImportBookingsModal.tsx`, an Import Duties CTA on AllBookingsPage, and `xlsx`.
`AddBookingDrawer` now creates through `createBooking` too, so both paths share
the fan-out. Three `.check.ts` files pass; build and lint clean.

Measurement prompted by a question about duplicates:

- **Inside the sheet:** none. Zero byte-identical rows, zero Travel IDs carrying
  two rows for one day. The importer collapses a repeated day to one duty and
  reports it anyway — the format does not prevent it.
- **Against the database:** the blanket `booking_ref` skip hid a data-loss path.
  5 of 261 Travel IDs span a calendar month, one across four months with 121
  duties. A client splitting a long trip across monthly exports would have every
  day after the first file silently dropped. `ReferenceData` now carries
  `existingDuties` (booking_ref → duty start_dates) instead of `importedRefs`,
  so a booking counts as imported only when the file adds nothing to it.

Merging into an existing booking was deliberately not built — it means widening
the booking's date range and reconciling against existing allotments. Reported
instead, which removes the silent loss without smuggling a second operation into
a bulk import. Both are now non-goals.

**Verdict.** 7 capabilities, 13 constraints, 11 non-goals, no open questions.
Spec and code agree.
