### Answered by the Figma

- **Q1 — do drivers see money? NO.** No rate, fare or earnings appears on any
  screen. Simplifies the driver RLS surface; rate columns must be withheld.
- **Auth model = Driver ID + static 4-digit code**, code generated at driver
  creation and shared out-of-band. User-stated. **Flagged as the run's primary
  architectural risk** — see open items.
- **Duty lifecycle as designed:** Start Duty → capture start KM + speedometer
  photo → Confirm pickup (or Mark no-show) → Close Duty.
- **Navigation:** three tabs — Current / Upcoming / Completed.

### Open items raised

- **OI-1 (blocker):** static 4-digit PIN is not a Supabase Auth primitive and
  collides with the `current_company_id()` RLS model. 10⁴ keyspace, no rotation,
  no lockout designed.
- **OI-2 (blocker):** no end-kilometre capture screen exists, yet it is the
  input the entire invoice depends on.
- **OI-3:** `Completed` tab has no design.
- **OI-4:** no empty states for any tab — including "no current duty", which is
  what a driver sees most of the day.
- **OI-5:** multi-day outstation duty not addressed (Q3 still open).
- **OI-6:** offline behaviour not addressed (Q4 still open).
- **OI-7:** Q2 (operator approval before invoicing) is an operator-side screen,
  not visible in this driver flow — still open.
- **OI-8:** Q5 (attendance auto-mark) absent from the design — still open.

### Round 3 — blockers resolved

- **Multi-day outstation: ONE slip.** A single signature and a single odometer
  pair at the very end, regardless of duration. **Consequence: actual readings
  and timestamps are columns on `duties`, not a child table.** This was the
  biggest schema fork and it is now closed in favour of the simpler shape.
- **Operator approval: NONE for now.** The passenger signature is the
  authority; a closed duty is immediately invoiceable. Revisit if disputes
  appear or a customer demands counter-sign.
- **Attendance: YES.** First `Start Duty` of a day marks that driver `P` in
  `driver_attendance`. Existing table, no schema change.
- **Signature attribution: not required.** Any passenger may sign. OI-10 closed
  — no signer-name capture.
- **Duty reference: use the existing `duties.id`.** No new ref column. OI-13
  closed; `#DT435632` in the mock is display formatting only.
- **Expenses generalised.** Not toll-only — the driver must be able to record
  any money they spent on the duty. OI-9 stands: capture screen still to design.
- **Offline: user asked for a recommendation** — recommendation given and
  **APPROVED**: queue writes on-device (IndexedDB, photos as blobs), flush on
  reconnect, explicit "saved on your phone" status. No full offline sync.
  Rationale: driver-entered readings are billing inputs and must never be lost,
  but the fields are single-writer so no conflict resolution is needed.
  `Upcoming` / `Completed` degrade to an offline state.
- **`Fuel entries` confirmed in scope for v1.** OI-11 becomes a design task.
- **Completed list + empty states + expense capture: owned by Sally.** OI-9 and
  OI-12 become design tasks, not blockers.
- **Discovery complete.** All blockers resolved; drafting.
