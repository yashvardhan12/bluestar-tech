## Intake (carried in from planning conversation)

Context inherited from the multi-tenancy implementation planning session that
preceded this run. Recorded as **intake, not decisions** — each still needs
confirmation from Yash during Discovery.

### System (brownfield, existing)

- Vite + React 19 + TypeScript + Tailwind CSS v4 + React Router v7 + Supabase
- Untitled UI token system already implemented in `src/styles/tokens.css`,
  registered via `@theme` in `src/styles/global.css`
- Brand primary `brand-600` `#155eef` · Inter · JetBrains Mono
- lucide-react icons at `strokeWidth={1.75}` · `clsx` for conditional classes
- Shell: 80px icon sidebar (`w-20`), 208px sub-nav (`w-52`), or horizontal tabs
- Existing primitives: Drawer (480px right slide-in), StatusBadge, ConfirmModal,
  ConfirmDeleteModal, ClearAllotmentModal, RestoreDutyModal, Toast, FileUpload

### What is being built

Single-tenant, no-auth app → multi-tenant. Parent "Bluestar Co." with multiple
child companies as tenants. Members log in via Supabase Auth (zero auth code
exists today) and are assigned to one or more companies via membership.

Two global roles: **Owner** (create/archive companies, change roles, sees all
companies) and **Admin** (everything else within their companies, including
member management and deletes). Tenant isolation enforced in Postgres via RLS,
leaving ~143 existing query sites untouched.

### New surfaces required

1. Login page — none exists
2. Company switcher, including "All companies" rollup mode
3. Settings rebuild — Account (real auth user), Team members (per-member company
   assignment), Companies (tenant CRUD with soft-delete/archive)
4. Email invite flow via Resend

### Open UX problems named at intake

- **(a) Ambient company awareness.** The 80px rail is peripheral vision; risk is
  users writing a booking into the wrong company without noticing.
- **(b) Rollup read-only legibility.** "All companies" is read-only by
  construction — the DB rejects writes when no active company is set. Needs to
  read as a deliberate reporting lens, not a broken workspace.
- **(c) Switcher appearance/disappearance.** Single-company members arguably
  shouldn't see a switcher, but a control materialising later when they're added
  to a second company is disorienting.

### Inherited constraint — state patterns

`ux-backlog.md` (2026-06-09) records two gaps that this build amplifies:

- line 43 — "No loading skeletons on tables"
- line 44 — "No error states or retry patterns — All Supabase fetch points"

Post-multi-tenancy an empty table becomes ambiguous across five meanings:
no data yet · wrong company · rollup mode · correctly filtered by RLS ·
incorrectly filtered by RLS. Flagged at intake as the highest-value part of
EXPERIENCE.md.

### Known design-system violation

`src/pages/settings/SettingsPage.tsx` uses `violet-*`, `green-*`, `blue-*`,
`purple-*` and raw hex `#e4e7ec` / `#98a2b3` instead of `brand-*` tokens. A
token cleanup is already scheduled in the same implementation pass, so
DESIGN.md should codify correct usage.

## Decisions

### DEC-1 — Working mode: coaching path
_2026-07-31 · resolves OQ-2_

Decisions get walked one at a time rather than batched. Creative tools (colour
themes, design directions, Excalidraw wireframes, HTML key-screen mocks) woven
into Discovery where seeing beats describing. Yash makes the picks; Sally
probes and renders, never imposes.

### DEC-2 — Stakes: internal tool
_2026-07-31 · resolves OQ-3_

Known users, trained on the job, problems fixable in person. Accessibility floor
still applies as a baseline; no gold-plating for anonymous or untrained users.

**[NOTE FOR UX]** Tension worth revisiting: the app carries invoices, receipts
and driver payroll, and the multi-tenancy build introduces company archive
(soft-delete of a tenant that owns financial records). "Internal tool" stakes
were chosen over "money is on the line", so destructive-action and
irreversibility patterns get baseline rigour by default. Flagging rather than
overriding — Sally to re-probe specifically at the archive-company and payroll
surfaces, where the cost of a mistake is out of proportion to the stakes level.

### DEC-3 — Morning scan: one company at a time, flipped fast
_2026-07-31 · resolves OQ-1 and T-1_

Hassel does **not** want a side-by-side overview. He picks a company, works it,
switches, repeats. No new dashboard surface is built.

Consequences:

- **The switcher carries the morning scan.** Hassel's step 3 ("how many duties
  for each company") still has to be answered somewhere. With no overview screen,
  the only place left is the switcher itself — it must show per-company duty
  counts, not just company names. The switcher stops being navigation and becomes
  Hassel's dashboard.
- **Speed is a stated requirement, not a nicety.** "Flipped fast" — keyboard
  access is in scope, not a stretch goal.
- **Rollup mode may be unnecessary.** T-1 dissolves rather than resolves: if
  Hassel never works across companies simultaneously, "All companies" read-only
  has no user behind it. See OQ-6.

### DEC-4 — Hassel writes in every mode
_2026-07-31 · locates the climax beat_

Step 4 "adjustments" is **all four** of: allotting vehicles and drivers, fixing
timings and duty details, reacting to problems (sick driver, vehicle in workshop,
customer moved a booking), and adding new bookings as the phone rings.

Hassel is a full operator, not a supervisor. **Climax beat = reacting to
problems** — the reshuffle under time pressure, where a driver has called in sick
and duties already allotted have to be re-cut.

### DEC-5 — Company switcher: sidebar only, nothing else
_2026-07-31 · supersedes the ambient-identity proposals_

The switcher lives in the existing sidebar and shows which company is active.
**No colour signature, no company name in page headers, no company banner inside
drawers.** Ship the simple version.

Rationale (Yash): the wrong-company-write risk is *hypothesised, not observed*.
Designing a mitigation before the problem is validated is speculative work.
Build the plain thing, watch what actually happens.

Sally's position: agreed and recorded without reservation. R-1 below is
downgraded from "risk to mitigate" to "hypothesis to validate" — see H-1.

### DEC-6 — "All companies" rollup mode: cut
_2026-07-31 · resolves OQ-6_

Hassel never views across companies (DEC-3), and no other user need surfaced.
The mode is removed entirely rather than kept speculatively.

**Downstream simplifications for the implementation plan:**

- `active_company_id` is **never null** — always exactly one active company.
- `visible_company_ids()` collapses to a single-value check:
  `company_id = current_company_id()`.
- Read-only mode disappears, and with it the whole "make read-only legible
  rather than broken-feeling" problem from intake.
- Writes can no longer fail closed on a null active company, so the
  "disable create buttons in rollup" UI requirement is void.
- **New requirement created:** first login has no active company set. Something
  must choose one — default to first membership. See OQ-7.
- Empty-table ambiguity drops from five meanings to four.

### DEC-7 — Error states serve two audiences
_2026-07-31_

When something breaks, Hassel **tries to figure it out himself first, then calls
Yash if it persists.** Every error state therefore carries two payloads:

1. **For Hassel** — plain language plus something to try. He is not helpless and
   will attempt recovery before escalating; an error that offers no action wastes
   that instinct.
2. **For Yash** — a diagnostic handle that survives the phone call. Without it,
   escalation degrades to "it didn't work" and Yash debugs blind.

Most error states serve neither. Exact shape pending — see OQ-8.

**Corollary — the empty state absorbs the wrong-company hint.** An empty result
is the one moment where "are you in the right company?" is genuinely useful.
Putting the hint there serves H-1 without contradicting DEC-5: no ambient
identity across the app, but a company cue exactly where it earns its place.

### DEC-8 — Error state: plain message + expandable technical detail
_2026-07-31 · resolves OQ-8_

Two-tier disclosure. Top tier is human ("Couldn't load duties. Something went
wrong on our end."), plus a retry action. Below it, a collapsed **Technical
details** disclosure carrying the real error — Postgres/Supabase code, surface
name, timestamp, active company.

Hassel expands it himself when self-diagnosing, and screenshots it when
escalating to Yash. Serves both audiences from one component. Default collapsed
so the technical layer never taxes the normal path.

Applies at **every** Supabase fetch point — closes `ux-backlog.md:44`.

### DEC-9 — Empty state: name the company, do not suggest others
_2026-07-31_

"No duties in Bluestar North for today." States scope so Hassel always knows
what he is looking at. **No cross-company nudge, no sibling-company list.**

Rejected the "offer the other companies" variant: it re-introduces ambient
cross-company navigation that DEC-5 deliberately removed. Naming the scope is
information; listing alternatives is a suggestion. Hassel uses the sidebar
switcher when he wants another company.

Empty states still carry the primary action for the surface (e.g. *Add booking*).

### DEC-10 — Switcher: rail badge opening a popover with duty counts
_2026-07-31 · resolves the DEC-3 / DEC-5 conflict_

The 80px rail (`w-20`) carries a company badge. Clicking it opens a popover
listing every company Hassel belongs to, each with its **total duty count**.

This reconciles the two decisions that appeared to collide: the switcher stays
in the sidebar and nothing else is added elsewhere (DEC-5), while Hassel's
morning scan gets a home (DEC-3). One click answers "how many duties in each
company"; a second click puts him in the one he wants.

Counts are **totals**, not attention-filtered — the "only show what needs you"
variant was rejected. Hassel asked for how many duties there are, not how many
are unalloted; filtering to exceptions answers a question he did not ask.

Implementation note: the counts need their own aggregate query, and it must run
**across** companies — i.e. it cannot be scoped by the active-company RLS policy
the way every other query is. This is the single exception to "the 143 query
sites are untouched". Flagged for the implementation plan.

### DEC-11 — Loading: skeleton rows, everywhere
_2026-07-31 · closes `ux-backlog.md:43`_

Skeleton placeholder rows in the table's own shape, on **all** tables — not just
the slow ones. Layout holds while data lands; no jump on arrival.

The "skeletons only where it's slow" variant was rejected explicitly: two
loading patterns in one app is the drift that produced the backlog item in the
first place. One pattern, applied uniformly.

### DEC-12 — Second protagonist: Yash, the infrequent Owner
_2026-07-31_

Yash is the sole Owner. He enters Settings **a handful of times a year** — when
the business opens a company, or when someone joins and needs access.

This inverts Hassel's brief. Hassel needs speed, repetition, minimal friction.
Yash needs **clarity over speed**, because by the time he returns he will have
forgotten how it works. Design consequences:

- Labels over icons. No learned-shorthand affordances.
- State the consequence *before* the action, not after — he has no muscle memory
  to fall back on.
- Never assume continuity between sessions. Each visit is effectively a first
  visit.
- Two surfaces, two design languages: **Settings is not a fast surface** and
  should not inherit the operational pages' density.

**This directly cashes the [NOTE FOR UX] under DEC-2.** Stakes were set at
"internal tool", but the archive-company action is performed rarely, by someone
with no recent practice, on a tenant that owns bookings, invoices and payroll.
That combination — infrequent + destructive + financial — earns more rigour than
the baseline stakes level implies. Re-probing now as promised.

### DEC-13 — Login: email + password
_2026-07-31_

Standard Supabase Auth email/password. Magic link rejected despite Resend already
being wired: Hassel signing in at 8am with the phone ringing should not wait on
an inbox.

Password reset flow is therefore in scope. Login is a **daily** surface for
Hassel — first thing he sees each morning — so it carries the app's first
impression despite being functionally trivial.

### DEC-14 — Companies cannot be removed at all
_2026-07-31 · supersedes the archive/soft-delete proposal_

No archive action, no delete action. Companies are **create and edit only**.

**This is a removal, not an omission.** `SettingsPage.tsx:946` currently performs
a hard `supabase.from('companies').delete()` via the row `⋯` menu behind a
standard confirm. Harmless today (nothing reads companies); catastrophic once a
company owns bookings, invoices and payroll. That action is deleted.

Consequences accepted:

- A company created by mistake is permanent. At Yash's usage frequency
  (DEC-12, "a handful of times a year") the risk of a stray company is low and
  the cost of a stray deletion is unbounded — an asymmetry that favours this.
- The "what happens to Hassel mid-session" edge case disappears entirely, along
  with the destructive-action rigour question raised under DEC-2 and DEC-12.
  **That thread is now closed.**

**[NOTE FOR UX]** Open for implementation, not for design: whether the DB keeps a
nullable `archived_at` column with no UI attached. Costs nothing now, avoids a
migration if "for now" ends. No UX consequence either way.

### DEC-15 — Company assignment: checklist inside the member drawer
_2026-07-31_

Editing a team member opens the existing 480px `Drawer`; company access is a
checkbox list sitting alongside name, email and role. One surface holds
everything about a person.

Chosen over the people × companies grid and over managing membership from the
company side. Rationale fits DEC-12: Yash visits rarely and thinks
person-first — "Hassel joined, give him access" — not matrix-first. The grid
answers a question he does not have.

Reuses an existing primitive, so no new component enters the system.

Known ceiling: degrades past roughly fifteen companies, where a flat checkbox
list stops being scannable. Not a concern at three.

### DEC-16 — First login: a one-time company chooser
_2026-07-31 · resolves OQ-7_

After Hassel's first successful sign-in, before he reaches any operational page,
he picks his starting company from a full-screen chooser listing every company he
belongs to with its duty count. He lands there and never sees the screen again.

Chosen over silently defaulting him into an arbitrary company, and over Yash
presetting it at invite time.

Rationale: the sidebar switcher is a badge in an 80px rail (DEC-10) — the *only*
signal that other companies exist. A member dropped straight into a duties page
may never discover it. The chooser is the one moment that teaches the switcher's
existence, and it pays for itself by making DEC-10 legible. It also uses the same
company + count pairing as the popover, so the pattern is learned once.

Cost accepted: one extra screen on one occasion per user.

### DEC-17 — Zero company access is prevented, not explained
_2026-07-31 · raised during distillation, not during Discovery_

Distilling the state table surfaced a case nobody had named: a member with **no
company memberships**. Invited, never ticked a company, signs in to a shell with
a rail and tables that render nothing.

Resolved by **prevention rather than an explanatory state**. The member drawer
requires at least one company before it will save.

Because DEC-15 puts invite and edit in the *same* drawer, a drawer-level
validation rule guards both paths — a member cannot be created without access,
and cannot have their last company unticked. The bad state is unreachable
through the UI, so no fallback screen is built.

The explanatory-state variant was rejected along with the belt-and-braces
"both" option.

**[NOTE FOR UX]** Residual, accepted: zero-access remains reachable by direct
database manipulation. Out of scope for UX — no screen exists for it, and a
member in that state sees an empty shell. Recorded so the omission is a decision
rather than an oversight.

never from **tenant** scoping, with the membership predicate inside the query.

_2026-07-31 · fixes adversarial critical #4_

### Round-2 revisions (2026-07-31)

Adversarial re-review: C2 and C3 **closed**, C1 **partial**, C4 **not closed on
the security half**, plus 3 new criticals created by the round-1 fixes.

### DEC-25 — Creating a company auto-joins its creator
_Fixes the Owner bootstrap deadlock_

Rule 3 (read-only own row) plus Rule 4 (Companies is edit-only) deadlocked: Yash
could create a company and never enter it. Flow 3 walked him through exactly that
without noticing.

Membership is now granted in the same transaction as creation. Deliberately the
narrowest exception to "nobody grants themselves access" — creation only, creator
only, that company only. Chosen over "Owners bypass membership entirely", which
would have widened the blast radius of a compromised Owner account.

### DEC-26 — Active company re-verified against membership on every read
_Fixes C4's security half_

`current_company_id()` resolves only if the user **is currently a member** of the
stored company, else resolves to nothing and fails closed.

**This restores the intersection DEC-6 removed.** Collapsing
`visible_company_ids()` to `company_id = current_company_id()` was logged as a
clean downstream win; it silently deleted the check that made isolation hold.
`SettingsPage.tsx:243` already writes to that table from the browser, so setting
the field must grant nothing.

### DEC-27 — Management visibility ≠ data access
_Fixes the Rule 6 / Foundation contradiction_

Owner sees every company **in the Companies management list**; operational data
still requires membership, for every role. Resolves the contradiction introduced
while fixing C2, without making Owner a bypass.

### DEC-28 — Member drawer saves a delta, never a replacement
_Fixes the C1 remnant_

An Admin's checklist is partial (rule 2), so whole-row saves silently revoked
invisible memberships. Saves now apply only within the editor's visible set.
Relatedly, "at least one company" validates against the member's **total**
memberships, resolving the rules 2/5 contradiction.

### DEC-29 — Company names unique; error never renders as empty
_Surviving round-1 findings_

Names must be unique, not just short codes — empty states quote the name, so
duplicates would break the disambiguation rule the whole state section rests on.

Separately: a failed fetch must never converge on the empty state. That is the
exact bug class that let a dead Settings page look like an empty one for two
months.

### DEC-30 — Two existing behaviours must be removed
_Code-level criticals surfaced by review_

`SettingsPage.tsx:216` self-provisions an `access_type: 'Owner'` row from the
browser — an Owner factory reachable by anyone who can load the app. Line 243
writes the profile row client-side, which becomes the attack path Rule 7a
neutralises. Both named in the spine as prerequisites.

DESIGN.md presented "41" under a **Usages** column. All 41 are token

### DEC-31 — Review closed; remaining items move to tests
_2026-07-31_

Three rounds have not closed: the cross-tab propagation window, fetch-dependency

### H-1 — Hypothesis: fast switching causes wrong-company writes

Hassel flips companies fast (DEC-3) and writes immediately in each — bookings,
allotments, timing edits (DEC-4). The hypothesis is that this produces
mis-scoped writes.

**Not designed for. Watch for it instead.** Signals that would confirm it:

- Hassel asking "where did that booking go?"

## Protagonist — Hassel

_Captured 2026-07-31 · narrated by Yash · **verbatim intake, gaps marked**_

Hassel manages **three companies**. Desktop/laptop, seated, morning. Not mobile,
not field. Form-factor resolves to **web, desktop-first**.

### The morning session

1. Opens his laptop.
2. Opens Bluestar.
3. Checks **how many duties there are for each company** — a cross-company scan,
   not single-company work.
4. **Makes adjustments.**
5. **Keeps track of how the duties are in all three, differently.**

**Climax beat — not yet located.** Steps 3→4 contain it (the moment he spots
something wrong and fixes it) but the narration doesn't yet say what he spots or
what "adjustment" means. Needs probing before the journey can close.

### What the current build gives him instead

Verified against code, 2026-07-31:

- **Lands on Duty Types.** Root route redirects to `/database/duty-types`
  (`src/App.tsx:43`) — a reference-data config screen.
- **No count exists.** `AllDutiesPage` paginates via `BATCH_SIZE` / `offsetRef` /
  `hasMore` and never totals. "How many duties" is unanswerable in the product.
- **No overview surface exists.** No dashboard, no home route with content.

### Surface closure — FAILS

Hassel's stated need (step 3) has **no surface**. Per workflow rules this is a
probe, not an invention: the missing screen is named here, not designed here.

### Tension T-1 — scan-then-adjust vs read-only rollup

Hassel's flow is **scan all three → adjust**. The architecture makes "All
companies" read-only by construction (DB rejects writes with no active company).
So the product forces **scan → switch company → re-find the thing → adjust**.

The intake framing ("rollup is a deliberate reporting lens, not a workspace")
was written before Hassel existed. His narration contradicts it: the rollup is
