# Spine Pair Review — bluestar

## Overall verdict

Structurally this is one of the more disciplined spine pairs you will see: DESIGN.md carries all eight canonical sections in exact order, EXPERIENCE.md carries all eight required defaults, every hex in the frontmatter was verified correct against `src/styles/tokens.css`, every code and commit citation resolves, and both files are lean enough that nothing reads as padding. The multi-tenancy core — switcher, chooser, badge, empty/error/loading states, the "name the company" rule — is committed, internally consistent, and directly source-extractable.

It breaks as a contract at the auth boundary. Login has a visual spec and no behavior, no invalid-credentials state, no password-reset surface (DEC-13 puts reset explicitly in scope), and no invite-acceptance surface (named as a required new surface at intake). The two-role model is declared in Foundation and then never expressed as a permission-denied state or a role gate on any IA row, in a product whose entire premise is permission filtering. One flow failure path instructs a consumer to build a screen that State Patterns and DEC-17 say must not exist.

A downstream consumer can build the multi-tenancy work from this pair today. It cannot build Login, invites, or role gating without going back to the log or to Yash.

## 1. Flow coverage — thin

Extracted every journey implied by the decision log (DEC-3/4 morning operation, DEC-12/15 infrequent-Owner administration, DEC-13 daily sign-in and password reset, DEC-16 first sign-in, DEC-17 zero-access prevention, intake "email invite flow via Resend") and by `ux-backlog.md`. Three Key Flows are present. All three are well-formed: named protagonist with role and time-of-day, numbered steps, an explicit bolded climax, a failure path. That part is genuinely strong and matches the reference spines' shape.

The misses are in what has no flow at all.

### Findings
- **high** The invite-acceptance journey has no flow, no IA surface, and no state. Intake names "Email invite flow via Resend" as one of four required new surfaces (`.decision-log.md`, "New surfaces required" item 4), and Flow 2 steps 1–2 depend on it ("Hassel gets an email... follows the link, sets a password") — but the link target is nowhere in the IA table (EXPERIENCE.md:42–56), has no component row, and has no states (expired link, already-accepted link, link for a revoked member). *Fix:* add an "Invite accept / set password" IA row, one Component Patterns row, and three State Patterns rows; or state explicitly that the invite link hands off to Supabase's hosted flow and is out of spine scope.
- **high** Password reset is entirely absent despite being explicitly scoped. DEC-13 states "Password reset flow is therefore in scope." EXPERIENCE.md never uses the word. DESIGN.md's Login card spec says "one text link" (DESIGN.md:174) without naming it, which is the only trace of the feature in either file. *Fix:* name the link, add the request-reset and set-new-password surfaces to IA, and add the "reset email sent" and "reset link expired" states.
- **high** Flow 2's failure path contradicts State Patterns and DEC-17. Flow 2 ends "Yash invited him but assigned no companies → the 'no companies assigned' state, naming who to ask" (EXPERIENCE.md:235–236), while State Patterns states "**No 'zero company access' state exists, by design**... that state is made unreachable rather than explained" (EXPERIENCE.md:133–137) and DEC-17 confirms "no fallback screen is built." A story-dev reading the flow builds a screen; one reading the state table builds none. *Fix:* delete the flow's failure line and replace it with the prevention rule — the member drawer would not have let Yash save without a company, so the failure is unreachable.
- **medium** The last-Owner protection rule exists only as a failure footnote in Flow 3 ("he tries to demote himself while he is the only Owner → blocked with an explanation", EXPERIENCE.md:251–252). It is a hard validation rule with the same shape as the ≥1-company rule, but it appears in no Component Patterns row, no State Patterns row, and no Multi-Tenancy Rule. Rules buried in flow prose get missed. *Fix:* promote it into the Member drawer row alongside the ≥1-company rule, and into Multi-Tenancy Rules as rule 8.
- **medium** Six of twelve IA surfaces have no flow and no surface-specific state, while the header claims "This spine covers the whole experience" (EXPERIENCE.md:15–16). Availability, Billing, Attendance & Payroll, Vehicle Tracker, Database and Settings → Account appear only as IA rows. The generic "Any table" state rows do cover their load/empty/error lifecycle, which is most of what they need, but the whole-experience claim overreaches — and `ux-backlog.md:16–19` records Billing → Invoices and Receipts as unbuilt "Coming soon" stubs, which the IA table lists as live surfaces without qualification. *Fix:* soften the scope line to "multi-tenancy plus the app-wide state contract," and mark build status on the IA rows that are stubs.
- **low** Flow 1 step 5 flattens DEC-4's four named write modes into a single line. DEC-4 locates the climax precisely at "reacting to problems," which Flow 1 does honor in step 6, but "adding new bookings as the phone rings" gets a half-clause at the end of the climax and "fixing timings" a three-word mention. *Fix:* fine as is if you accept the compression; DEC-4 is preserved in the log either way.

## 2. Token completeness — adequate

Extracted all 13 color tokens, 1 typography token, 3 radius tokens, and 4 component objects from the frontmatter, plus every token named in prose. **Every hex was checked against `src/styles/tokens.css` and every one is correct** (brand-50/100/600/700, error-50/500/600/700, warning-50/500, success-50/600 all match lines 35–83). No color token is missing a hex. No `{path.to.token}` reference in the components block dangles.

On the inheritance boundary, which is the load-bearing question here: it is stated clearly. The `inherits:` frontmatter key names the system and both files that carry it, each frontmatter block carries a comment saying what is inherited versus enumerated, and Brand & Style paragraph 2 states the two jobs the file exists to do. A consumer reading this knows gray/spacing/type-ramp come from `tokens.css` and the brand/semantic subset is enumerated here. That is the right call and better executed than the shadcn reference example, which relies on comments alone.

The weak spot is `rounded`, where the file stops inheriting and starts minting.

### Findings
- **medium** `rounded` invents three alias names with literal px that do not map to the inherited scale, and the values contradict the codebase. `input: 8px`, `card: 12px`, `popover: 12px` (DESIGN.md:36–40) correspond to `--radius-md` and `--radius-xl`, but neither inherited name is given. Meanwhile the app uses `rounded-lg` (`--radius-lg`, 10px) 266 times against 60 for `rounded-xl` and 28 for `rounded-md`. So Shapes (DESIGN.md:145–149) either silently mandates restyling the dominant radius across the app, or is wrong about the system it claims to codify. Neither is stated. *Fix:* replace the aliases with inherited names (`rounded: {md, lg, xl}` referencing `tokens.css`), then decide explicitly whether 10px stays as the card radius or the app gets restyled, and say which.
- **medium** `typography.page-title` mints a 30px literal that already exists as an inherited token, in a file whose Brand & Style says it "adds **no new palette and no new type ramp**" (DESIGN.md:72–73). `--font-size-display-sm: 1.875rem /* 30px */` is at `tokens.css:410`. The frontmatter comment two lines above the token says "No overrides." *Fix:* `page-title: { note: 'display-sm / line-height-xl, semibold' }` or delete the token and keep the prose sentence.
- **medium** No contrast target appears anywhere in DESIGN.md, and EXPERIENCE.md's Accessibility Floor points at it for exactly that ("Visual contrast inherits Untitled UI's verified ratios; see `DESIGN.md`", EXPERIENCE.md:156–158). The pointer dead-ends. The load-bearing new combination is the company badge, `brand-700` glyph on `brand-50` fill, which computes to 5.79:1 and passes AA — but nobody reading this pair knows that, and the same is unstated for JetBrains Mono technical text on `gray-50` inside the error block and for `gray-100` skeletons on white. *Fix:* one line in DESIGN.md Colors stating the AA target and naming the three new combinations as verified.
- **medium** `company-switcher-popover.background: '#ffffff'` (DESIGN.md:49) is a raw hex in a file whose Do's and Don'ts says "Don't hardcode hex" (DESIGN.md:185) and whose Colors section spends a whole subsection eliminating two hardcoded values from `SettingsPage.tsx`. `--color-white: #ffffff` exists at `tokens.css:12`. *Fix:* `'{colors.white}'` and add `white` to the enumerated colors block.
- **low** The components block mixes reference syntax with bare name-strings. `background: '{colors.brand-50}'` resolves; `border: 'gray-200'`, `background: 'gray-100'`, `detail-background: 'gray-50'` are literal strings that no resolver can flatten, because gray is deliberately not enumerated. Human consumers are fine; a machine consumer flattening component tokens gets the string `gray-200` with no value. *Fix:* either enumerate the four grays actually used in components, or note in the block comment that gray values resolve at the Tailwind layer, not in this file.
- **low** Eight of thirteen enumerated colors are referenced nowhere in either spine: `brand-100`, `error-50`, `error-600`, `error-700`, `warning-50`, `warning-500`, `success-50`, `success-600`. The block comment frames this as a permission list ("names the subset the multi-tenancy surfaces are permitted to use"), which justifies it, but nothing in the pair uses warning or success at all. *Fix:* keep if the permission framing is intended; otherwise trim to what the build touches.

## 3. Component coverage — adequate

Extracted every component named in either file. DESIGN.md.Components carries 6 inherited-unchanged plus 8 new with real visual specs (anatomy, fill, glyph, radius, tier structure). EXPERIENCE.md.Component Patterns carries 8 rows, and the rules are real behavioral rules, not one-word descriptions — the Member drawer row in particular does load-bearing work by stating the ≥1-company constraint and explaining why one rule guards two paths. Both tables are above the bar set by the reference spines.

Two components exist on only one side, and one referenced component does not exist at all.

### Findings
- **high** Login card has a visual spec (DESIGN.md:173–174) and no behavioral row anywhere. It is Hassel's daily first surface by DEC-13's own framing ("Login is a **daily** surface for Hassel... it carries the app's first impression"). Nothing specifies what the text link does, what submit does, whether the email field is remembered, or what happens on failure. *Fix:* add a Login row to Component Patterns covering submit, the reset link, and field retention on failure.
- **medium** `ConfirmModal` is listed as inherited-unchanged and do-not-restyle (DESIGN.md:154) but no such file exists — `src/components/ui/` contains ClearAllotmentModal, ConfirmDeleteModal, DateRangePicker, Drawer, Field, FileUpload, RestoreDutyModal, StatusBadge, Toast. The error is inherited from `CLAUDE.md:58`, which is itself stale. A consumer told to reuse it will go looking. *Fix:* drop it from the list and fix `CLAUDE.md:58` in the same pass.
- **medium** Name drift on the same component. DESIGN.md specifies "**Company access checklist** — a checkbox list inside the member `Drawer`" (DESIGN.md:177–178); EXPERIENCE.md has no row of that name and folds the behavior into "Member drawer" (EXPERIENCE.md:98). Cross-file lookup by name fails in both directions. *Fix:* pick one name and use it in both files; "Member drawer" reads better as the surface, with the checklist as its sub-part in both specs.
- **low** "Company row menu" (EXPERIENCE.md:99) has a behavioral row and no DESIGN.md visual spec. Its rule — edit only, no delete, no archive — is the visible consequence of DEC-14, so the absence matters more than a normal row-menu would. *Fix:* one line in DESIGN.md Components, or fold the rule into Do's and Don'ts.
- **low** `StatusBadge` and `FileUpload` appear in DESIGN.md's inherited list and are never mentioned in EXPERIENCE.md, though Flow 3 step 2 implies FileUpload ("signature"). `Toast` is used in two State Patterns rows and Flow 1's failure with no Component Patterns row of its own. All three are inherited-unchanged, so this is defensible. `DateRangePicker`, `Field`, `ClearAllotmentModal` and `RestoreDutyModal` exist in the repo and appear in neither file. *Fix:* optional; if the inherited list is meant to be exhaustive, complete it, otherwise say it is illustrative.

## 4. State coverage — thin

Walked all twelve IA surfaces against the standard state set. On the axis this spine chose — table lifecycle — it is excellent and clearly the best-argued section in the pair: cold load, background refetch, empty-no-data, empty-filtered, fetch error, save error, session expired, not-signed-in, and switching-company are all covered with specific, implementable treatments, and the four-meanings table (EXPERIENCE.md:110–116) earns its space by making the "name the company" rule non-negotiable. Nine rows is more than either reference spine carries.

The section declares itself "the highest-value section of this spine, and the reason it was written." Held to that bar, the gaps are on the axis the product's own premise demands.

### Findings
- **high** No permission-denied state exists anywhere. Foundation declares two roles with distinct capabilities — Owner creates companies and changes roles, Admin does not (EXPERIENCE.md:31–36) — and IA lists Settings → Companies as a surface (EXPERIENCE.md:55) with no role note. What an Admin sees there is unspecified: hidden nav row, visible-but-disabled, or a denied screen. Same for the role field in the member drawer. The shadcn reference spine carries a permission-denied row for a far simpler role model. *Fix:* add a permission-denied row stating the posture (hide versus disable versus explain), and mark Owner-only rows in the IA table.
- **high** No invalid-credentials state on Login. The state table's only Login rows are arrivals — "Session expired → redirect to Login with a line explaining why" and "Not signed in → redirect, preserving destination" (EXPERIENCE.md:129–131). Wrong password, unknown email, and rate-limited/locked are all unspecified on the surface Hassel touches every morning. Voice and Tone gives no example for it either. *Fix:* one state row plus one Voice and Tone line; the tone question (name the failure versus stay vague) is a real decision that should be committed here.
- **high** The single-company member case is unresolved and uncarried. Intake named it as open UX problem (c) — "single-company members arguably shouldn't see a switcher, but a control materialising later when they're added to a second company is disorienting" — and no DEC resolves it. EXPERIENCE.md says the popover "lists every company the user belongs to" (EXPERIENCE.md:93) and the chooser is shown at first sign-in (EXPERIENCE.md:94), neither qualified for a list of one. A consumer must guess whether a one-company user gets a one-row chooser and a badge that opens a one-row popover. *Fix:* commit it in one line — the consistent answer is "yes, always, unconditionally," which matches DEC-16's own rationale that the chooser exists to teach the switcher.
- **medium** The switcher's duty-count query has no loading or failure state. Multi-Tenancy Rule 7 flags it as the single query that crosses companies and cannot be RLS-scoped (EXPERIENCE.md:195–198), and Flow 1 step 3 makes it Hassel's entire morning scan. If it is slow or fails, the popover shows what — no counts, zeroes, skeletons, an inline error? Zeroes would be actively wrong. *Fix:* one state row; the counts are the one place where a failed aggregate reads as real data.
- **medium** Multi-Tenancy Rule 3 ("**Every empty state names its company**", EXPERIENCE.md:183–184) has an unstated exception. Settings → Companies and Settings → Team members are not company-scoped surfaces — an empty companies list cannot name the active company without being nonsense. The rule is stated absolutely, in the section that calls it "the load-bearing rule of the whole build." *Fix:* scope the rule to company-scoped surfaces and say what the Settings empties say instead.
- **low** No offline or connection-loss row. Both reference spines carry one. Defensible for a seated desktop internal tool, but the Interaction Primitives ban on "silent failure of any kind" implies a network drop needs a treatment. *Fix:* one row, or an explicit "not designed for" line.
- **low** No loading treatment for pagination. `AllDutiesPage` pages via `BATCH_SIZE`/`offsetRef`/`hasMore` per the log's verification notes, so "load more" is a second loading moment that the "one loading pattern everywhere" rule (DEC-11) should govern. *Fix:* extend the cold-load row to cover appended batches.
- **low** The "Empty — no data" treatment gives duty-specific copy as the generic template: `"No duties in {company} for today."` on surface "Any table" (EXPERIENCE.md:125). Invoices and drivers are not "for today." *Fix:* `"No {records} in {company}."` with the date qualifier noted as duties-only.
