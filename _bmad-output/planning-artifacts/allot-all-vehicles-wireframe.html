All Vehicles Escape Hatch

A second view behind each allotment step, for the times the right vehicle — or the right driver — is the one the filters just hid.

The problem

Both steps filter twice, and neither announces it

Step 1 narrows the vehicle list twice before the operator sees a single row. Step 2 does the same to drivers. Every one of these filters is correct most of the time. None of them can be turned off.

The group filter keys off duty.vehicle_group — the value stored on the duty and shown in its info table, derived from the duty type back at booking time. This spec keeps it there rather than re-deriving from duty_types.

FILTER 1 — GROUP vehicle_groups.name = duty.vehicleGroup
FILTER 2 — TIME no overlapping non-cancelled duty in the window
FILTER 3 — DRIVER STATUS status IN ('Active', 'Available')
FILTER 4 — TIME, AGAIN same overlap rule, applied to drivers

So when the right answer is “put the Innova on it even though this is a Sedan booking”, or “that vehicle finishes at 14:00 and the duty starts at 18:00, whatever the data says”, there is no way through the screen.

Today the operator closes the drawer and edits the booking’s vehicle group instead — corrupting a booking record to get around a UI limit. That workaround is the real cost of the missing control.

The decision

The default view pays nothing

The screen an operator sees ninety times out of a hundred should not carry the controls for the other ten. Every filter, every switch, every count belongs behind a door — and the door is a single tertiary button.

So there are two views, not one screen with modes:

View 1 — Assign Vehicle. Byte for byte what ships today: free vehicles in the duty’s own group, nothing else. One low-emphasis button in the corner.

View 2 — All vehicles. A dedicated surface, reached deliberately, with room to hold the controls properly: group, search, and an Include on-duty switch.

Splitting the views is also what lets the two filters stay honest. Group is a scope choice — which class of vehicle goes on this job, made constantly, zero risk. Availability is a safety line — the one action here that can write bad data. On a shared control row they blur together; on a dedicated view they can be shaped differently and read differently.

What View 2 can reach, from a Sedan duty on a 41-vehicle fleet — the operator always knows which of the two things they relaxed:

Sedan · include on-duty10

Row 1 is View 1, so the door opens onto familiar ground. Rows 2–4 are the operator widening deliberately, one axis at a time. An earlier draft of this spec jumped straight from 6 to 41 in a single toggle — landing on 41 rows in one move, nobody can tell why any given row is in front of them.

View 2 · the group menu

Narrowing back down, once you are inside

View 2 opens on All groups. This menu is how an operator narrows again — to the SUVs, say, when they know the substitute is a class up rather than a specific vehicle.

Counts sit in the options and respond to the on-duty switch. That is what makes the two controls legible as a pair: with the switch off, a group reading 0 tells the operator that narrowing the group will not help and the switch is the thing they actually need.

Drivers

The same door, but not the same room behind it

Assign Driver has the identical dead end, so it gets the identical door: View 1 stays as it ships, one tertiary button opens View 2. But the axes underneath are not the vehicle axes, and copying them literally would produce a wrong screen.

A vehicle’s group is a scope — harmless, routine. A driver’s status is 'Active' | 'Inactive' | 'Available' | 'Assigned' | 'Unavailable', and those five split three ways, not two:

ROUTINE — ASSIGNED a good driver, just spoken for by a vehicle. The real analogue of “other vehicle group”. Mark it, never warn.
FLAGGED — INACTIVE / UNAVAILABLE should not be driving today. Not a time conflict — a second, different warning.
SAFETY LINE — ON DUTY overlaps this duty window. Same rule as vehicles, same switch.

So a driver row can carry two unrelated warnings at once where a vehicle row could only carry one. That is the whole difference, and it lives in the row and the warning bar — not in a third control.

One thing the current filter misses entirely, worth knowing before you build: drivers.off_day and the driver_attendance table are not consulted at all. A driver on their weekly off, or marked absent today, shows up as perfectly available. Out of scope here; flagged below.

What the data layer needs

Two queries relaxed, two new values in the step machine

  1. Drop .eq('vehicle_groups.name', …) — keep the join to read the group name. Today vehicleGroup is hardcoded from duty.vehicleGroup because the filter guaranteed it; in All mode it has to come from the row.
  2. Stop discarding busy vehicles — annotate them. busyByVehicle already holds the intervals. isFree() becomes a flag on the row instead of a .filter().
  3. Add id and booking_id to the busy-duty select so the warning bar can name the conflicting duty.

The drawer already runs a step machine — useState<1 | 2>. The two browse views are two more values, 'all-vehicles' and 'all-drivers', not new components: same list markup, same handleNext / handleSave, different props. Back returns to the view that opened it; picking falls through exactly as it does today.

Drivers need the mirror of the same three edits: drop the .in('status', …) in the browse view and keep status on the row; stop discarding busy drivers and flag them instead; add id to the busy-duty select so the warning can name the duty. One extra join — vehicles!assigned_driver — supplies the “Assigned · Dzire KA01 AB 1234” subline.

Every combination comes from one fetch of the whole fleet. Filter in memory when either control changes — no refetch, no spinner, and all the per-group counts in the menu are free.

One build note: SelectField is currently copy-pasted in VehiclesPage, DutyTypesPage and AddBookingDrawer. Lift one into components/ui/ and use it here rather than writing a fourth — the Field consolidation in cc97427 is the cautionary tale.

Signed off

Decided, and deliberately deferred

Settled

Drivers get the same door

Views 3 and 4 ship in this pass, alongside vehicles. The button, its placement and its weight are identical; only the axes behind it differ.

Settled

The browse views remember nothing

Every duty opens on View 1, including the next duty in a bulk allotment. The default is the safety, and one click is cheap. Revisit only if someone is watched doing twenty substitutions in a row.

Later

A double-booking leaves no trace

Two duties on one vehicle, or one driver, with nothing in the data marking that a human overrode the check. Fine while allotment is a judgement call. It stops being fine the moment duty slips, payroll or availability reporting start assuming one vehicle, one duty — so this is the thing to come back to before any of those grow teeth. Carry it into the code as a ponytail: comment at the override site so it is findable, not just remembered.

Later

Driver availability ignores leave entirely

Neither drivers.off_day nor driver_attendance is consulted. A driver on their weekly off, or marked absent this morning, reads as fully available in every view including View 3. Found while speccing View 4; not part of this change, and worth its own pass.
